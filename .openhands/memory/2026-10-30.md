## Expensive lessons
- The web app is **inlined** `@phirst/core`; after a core change rebuild core *and* web and
  restart `next start`, or you get stale-bundle bugs.
- Build web with `NODE_ENV=production npm run build -w @phirst/web` — the sandbox's global
  `NODE_ENV=development` breaks `next build`.
- `apps/web` has **no** `.env.local` here; env lives in the repo-root `.env` (root `.gitignore`
  ignores `.env`). `next.config.mjs` proxies `/api/*` to `PHIRST_API_INTERNAL ?? :12001`.
- Start services: `npm run start:api` (root, tsx) and `npm run start -w @phirst/web` from
  `apps/web`. Logs to `.run/` (gitignored).
- Postgres runs in container **`phirst-pg`** (user `phirst`, db `phirst`). Fresh DB →
  `ownerExists:false`, so run `/api/auth/setup` first.
- `case` globs in bash do **not** support `\|` alternation — a smoke assertion using it
  silently never matches. Use a plain substring.

## Incident — "the link is dead" (2026-10-31 01:37 UTC)
**Symptom:** the public work-1 URL returned 200 and the app HTML loaded, but the page was
**completely unstyled** (looked dead/broken to the owner).
**Root cause:** running `NODE_ENV=production npm run build -w @phirst/web` during pre-push
verification replaced `apps/web/.next/` **while `next start` was still serving**. The running
server kept the old build manifest in memory and emitted HTML referencing
`/_next/static/css/8666ab…css`, a file that no longer existed on disk (it had been replaced by
`f807cb…css`). That CSS request returned **400**, so every style was missing. HTML/JS/API all
returned 200, which is why a naive reachability check said "healthy".
**Diagnosis that worked:** compare the CSS href in the *served* HTML against the files in
`apps/web/.next/static/css/`. A mismatch = stale server.
**Fix:** `kill <next-server pid>` then restart `npm run start` from `apps/web`. CSS then 200s.
**Rule:** never run a production build while `next start` is serving. Rebuild first, *then*
restart. A 200 on `/` is not proof the app is healthy — check a static asset too.

## Recovery after a sandbox runtime reset (2026-10-31 06:23 UTC)
The runtime pod was recreated (`runtime-…-64cf7dcdbd-vpx89`); **everything was gone**:
no Docker daemon, no Postgres, both services dead, empty `.run/`. The hostname
`work-1-kznopodrculyuhfn.prod-runtime.all-hands.dev` is **stable across resets** (it is
derived from the runtime id in `RUNTIME_URL`), so the link is reusable — only the processes
and containers die. `git` and the working tree survived; `.env` survived.

Bring it back in this order (all verified):
1. `sudo dockerd >/tmp/dockerd.log 2>&1 &` then wait ~12s for the socket.
2. `sudo docker run -d --name phirst-pg -e POSTGRES_USER=phirst -e POSTGRES_PASSWORD=phirst_dev_pw -e POSTGRES_DB=phirst -p 5432:5432 postgres:16-alpine`
3. `sudo docker exec phirst-pg psql -U phirst -d phirst -c "CREATE DATABASE phirst_test OWNER phirst;"`
4. `npm run migrate` (applies 0001 + 0002).
5. `npm run start:api` → wait ~12s → `/api/health`.
6. From `apps/web`: `npm run start` → wait ~14s. `apps/web/.next` survived, so no rebuild needed.
7. Fresh DB means `ownerExists:false` → re-run `POST /api/auth/setup` to recreate the owner,
   then re-connect the **paper** broker and re-activate it (broker rows are in the DB too).
8. `(setsid nohup ./scripts/wein-supervise.sh >/dev/null 2>&1 &)` to survive a process death.

Note: `docker run` returned the container id but `psql` failed on the first attempt because
Postgres was still initialising; the container reported `Up` immediately. Poll
`docker exec phirst-pg pg_isready -U phirst` before using it.
